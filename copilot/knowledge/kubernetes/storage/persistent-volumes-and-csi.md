# Persistent volumes, claims, StorageClasses and CSI

## Summary
**TL;DR:** A pod asks for storage with a **PersistentVolumeClaim** (PVC: size, access mode, class). A **PersistentVolume** (PV) is the actual piece of storage, created by an admin in advance (static) or on demand by a **StorageClass**'s provisioner (dynamic), today almost always a **CSI** driver. Binding is one-to-one. Access modes describe how many **nodes** (or pods) may mount it: `ReadWriteOnce` = one node, `ReadWriteOncePod` = one pod, `ReadOnlyMany`/`ReadWriteMany` = many nodes. The reclaim policy decides what happens to the data when the claim is deleted: `Delete` (default for dynamic volumes) or `Retain`.
**Use this when:** a PVC is `Pending`, a pod cannot attach a volume on another node, you choose a StorageClass, or you must make sure data survives a claim deletion.
**Not this doc:** Secret, ConfigMap and projected volumes → `kubernetes/volumes-secrets-and-projected.md`; per-pod claims of StatefulSets → `workloads/workload-controllers.md`.

## Problem
Data lost because a dynamically provisioned volume had `reclaimPolicy: Delete`; a second replica stuck because the volume is `ReadWriteOnce` and the pod landed on another node; a PVC `Pending` "forever" that is actually waiting for its first pod. All follow from the claim/volume/class model.

## Mental model
**Analogy:** renting storage units. The PVC is your rental request ("1 GiB, one key holder"). The PV is a specific unit. The StorageClass is the rental company's product line, with a robot that builds a new unit when someone asks (dynamic provisioning). Access mode is the key policy. The reclaim policy is the contract clause: when you cancel, the unit is demolished (`Delete`) or locked and kept for the landlord to clear out (`Retain`).

**Artifact:** a dynamically provisioned claim in the lab (k3s v1.33.5, local-path provisioner, 2026-11-04) ✅[^4]:
```console
$ kubectl get sc
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false
$ kubectl get pvc data            # right after creation
data   Pending                                      local-path
$ kubectl get pvc data            # 20 s later, after the pod using it was scheduled
data   Bound    pvc-9ae29a74-90b9-4683-a972-1aaf45f1d54f   1Gi   RWO   local-path
```

## How it works
**4 actors:**
- **PVC** — its job: request storage for a namespace ✅[^1].
- **StorageClass + provisioner (CSI driver)** — its job: create volumes on demand with class parameters ✅[^1] ✅[^2].
- **PV controller** — its job: bind each claim to exactly one matching volume, via a two-way `claimRef` ✅[^1].
- **kubelet + CSI node plugin** — its job: attach and mount the volume into the pod on its node ✅[^5].

1. **Claim:** the PVC names a class, size and access mode. A claim with `storageClassName: ""` opts out of dynamic provisioning ✅[^1].
2. **Provision:** if no existing PV matches and the class has a provisioner, a PV is created ✅[^1]. With `volumeBindingMode: WaitForFirstConsumer` this waits until a pod using the claim is scheduled, so the volume is created where the pod runs (the lab's PVC was `Pending` until then) ✅[^4] ✅[^6].
3. **Bind:** one PV ↔ one PVC; a claim stays unbound until a matching volume exists ✅[^1].
4. **Use:** the pod references the claim; the volume is attached and mounted on the node.
5. **Protection:** PVCs used by a pod, and PVs bound to PVCs, are not removed until no longer in use (finalizers) ✅[^1].
6. **Release:** deleting the PVC applies the PV's reclaim policy: `Delete` removes the PV and the storage asset; `Retain` keeps it for manual cleanup; `Recycle` is deprecated ✅[^1]. Dynamically provisioned volumes inherit the class's policy, default `Delete` ✅[^1].
7. **Expansion:** if the class has `allowVolumeExpansion: true`, editing the PVC's size grows the volume; shrinking is not supported ✅[^2].

**Access modes** ✅[^1]:

| Mode | Short | Meaning |
|---|---|---|
| `ReadWriteOnce` | RWO | Read-write by a **single node** (several pods on that node may use it) |
| `ReadOnlyMany` | ROX | Read-only by many nodes |
| `ReadWriteMany` | RWX | Read-write by many nodes (needs a shared filesystem backend) |
| `ReadWriteOncePod` | RWOP | Read-write by a **single pod** in the whole cluster; CSI volumes only |

## Worked example
The lab PV behind the claim (2026-11-04) ✅[^4]:

| Field | Value | Meaning |
|---|---|---|
| Name | `pvc-9ae29a74-…` | Generated by dynamic provisioning |
| Capacity / mode | 1Gi / ReadWriteOnce | From the claim |
| Reclaim | `Delete` | Deleting the PVC deletes the data |
| Path | `/var/lib/rancher/k3s/storage/pvc-…_default_data` | local-path stores data on the node's disk: the pod is pinned to that node |

Making data survive: before deleting a claim whose data matters, patch the PV to `Retain` (`kubectl patch pv <pv> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`) (lab: after the patch, deleting the PVC left the PV `Released` with policy `Retain`) ✅[^4], or use a StorageClass whose policy is `Retain`.

## Edge cases
| Case | What happens | Why |
|---|---|---|
| PVC `Pending`, class uses `WaitForFirstConsumer` | Normal until a pod uses it | Delayed binding ✅[^4] |
| PVC `Pending`, no default class and no `storageClassName` | Waits for a matching static PV | Nothing to provision ✅[^1] |
| Deployment with 2 replicas sharing an RWO claim | Second pod cannot start if scheduled to another node | Single-node mount ✅[^1] |
| Two default StorageClasses | The most recently created default is used | Avoid more than one default ✅[^2] |
| Deleting a PVC in use | Stays `Terminating` until the pod is gone | Storage object in use protection ✅[^1] |
| Node-local storage (local-path, hostPath) and node failure | Data unavailable with the node | Volume lives on one node ✅[^4] |

## Takeaways
- Know each class's reclaim policy; use `Retain` (or backups) for data you cannot lose. [rule-candidate]
- Use RWO/RWOP for single-writer databases and a true shared filesystem for RWX.
- Prefer `WaitForFirstConsumer` classes in multi-zone clusters so volumes are created where pods run.
