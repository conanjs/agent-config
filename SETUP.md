# Setup

This file is written to be fed to an AI agent (Claude Code, Copilot CLI, etc.) on a machine that just cloned this repo — not primarily for a human to read step-by-step. Give the agent this file and let it execute the steps below.

## Steps (agent: do these in order)

1. **Detect the OS** you're running on.
2. **Run the installer for that OS:**
   - macOS/Linux: `./installers/install.sh`
   - Windows (PowerShell): `.\installers\install.ps1`

   This applies `mapping.yaml` — symlinks the knowledge base, instructions, etc. into place, and seeds `global-variables.md` to `{{AGENT_HOME}}/global-variables.md` (only on first run; a second run won't touch it again). If the installer's output includes a "Backed up pre-existing content to: ..." line, real pre-existing content was moved there rather than overwritten — mention this to the user rather than staying silent about it, especially if anything backed up looks like it might have held content they cared about.

3. **Detect this machine's repo clone path yourself** — don't ask the user to type it. From inside the repo, run `git rev-parse --show-toplevel` (or the equivalent for your shell). This is the value `{{AGENT_CONFIG_REPO}}` needs.

4. **Write that path into the deployed `global-variables.md`** — open `{{AGENT_HOME}}/global-variables.md` (i.e. `~/.copilot/global-variables.md` or `%USERPROFILE%\.copilot\global-variables.md`) and replace the `{{AGENT_CONFIG_REPO}}` row's `<SETUP REQUIRED>` value with the path you detected in step 3.

5. **For each company folder under `{{AGENT_HOME}}/companies/`, detect that company's repo-root variable too** (e.g. `{{OTS_REPOS_ROOT}}` for `companies/ots/`). This isn't a git repo path itself — find it by locating any one of that company's known repos on disk (check `companies/<company>/index.md`'s repo table for real repo names, e.g. `ne-api-gateway`) and taking its parent directory. If none of the listed repos exist on this machine yet, leave the row as `<SETUP REQUIRED>` and tell the user rather than guessing.

6. **Show the user every variable you filled in (step 4 and step 5) and ask them to confirm each is correct** before considering setup done. Don't silently assume detection was right — a wrong path is exactly the kind of error that's easy to miss later, so a human check here matters even though the detection itself is automatic.

7. **Verify the whole chain resolves:** read `{{AGENT_HOME}}/knowledge/documentation/doc-template-base.md` and confirm you can actually open it. If that works, `{{AGENT_HOME}}` resolution is proven end-to-end.

8. **Mention `{{LANGUAGE}}`** (default: English, in `global-variables.md`) to the user in case they want to change it now — don't change it yourself without being asked.

9. **Check `{{REFERENCE_REPOS_ROOT}}`** in `{{AGENT_HOME}}/global-variables.md` (where stack reference repos get cloned; default `~/agentic-sdlc-references`). On a machine set up before 2026-10-27 the row is missing, because `global-variables.md` is seed-once: copy the row from this repo's `global-variables.md`. **Set the path now; clone later.** Each reference is cloned the first time a project needs it: at project bootstrap for a detected stack (`{{AGENT_HOME}}/procedures/bootstrap-agentic-sdlc.procedure.md` step 4), or when a stack is chosen. Ask the user only whether they want to pre-clone now, for stacks they already work in; if yes, follow each `{{AGENT_HOME}}/frameworks/agentic-sdlc/stacks/<id>/reference.md` "How to fetch".

10. **Enable the doc checks in this clone:** `pnpm install` (test dependencies: Cucumber.js), then `git config core.hooksPath .githooks`. The pre-commit hook then runs `scripts/check-docs.sh` (the knowledge, procedures, agentic-sdlc and agent-foundry validators, then the Cucumber scenarios in `tests/`; needs Node.js 24, the version in `.nvmrc`, found automatically under nvm) whenever a commit touches `copilot/knowledge/`, `copilot/procedures/`, `copilot/frameworks/{knowledge,agentic-sdlc,agent-foundry}/`, `tests/` or the test setup files. Claude Code sessions in this repo run the same check after each edit (`.claude/settings.json`), and CI runs it on every push (`.github/workflows/validate-docs.yml`). Confirm with `git config core.hooksPath` → `.githooks`.

11. **Turn on the tracker reminder in Claude Code** (`specs/015-tracker/`). The installer links `~/.copilot/tracker`, and Copilot CLI picks up `~/.copilot/hooks/tracker.json` by itself. Claude Code reads hooks from `~/.claude/settings.json`, which is seed-once: a new machine gets the `SessionStart` hook from `claude/settings.json`, but on a machine set up before 2026-10-30, ask the user to merge that `hooks.SessionStart` entry into their `~/.claude/settings.json` (back it up first). Don't edit it for them. Confirm: start a session in a repo with a `TRACKER.md`; the open items show at the top. **Codex:** the installer links `codex/hooks.json` to `~/.codex/hooks.json`. Codex then lists the hook in `/hooks`, and it runs only after the user trusts it there.
12. **Turn on the turn token report** (`specs/017-turn-token-report/`). It lives in `copilot/hooks/turn-tokens/`, already linked through `~/.copilot/hooks`. **Codex:** the installer links `codex/hooks.json` to `~/.codex/hooks.json`, which now has a `Stop` hook; open `/hooks` in Codex and trust it, or it is skipped. **Claude Code:** `~/.claude/settings.json` is seed-once, so on a machine set up before 2026-10-31 ask the user to merge `hooks.Stop` and `statusLine` from `claude/settings.json` into it (back it up first; an existing `statusLine` is theirs to keep or replace). Don't edit it for them. Confirm: after the next turn a report starts with "Turn <n> ·", and `~/.claude/turn-tokens/` or `~/.codex/turn-tokens/` holds `<session id>.jsonl`. The 5-hour and weekly limits of Claude Code show only where its status line runs: a terminal session. The desktop app does not run status lines (tested 2026-10-31), so there the report says the limits are unknown and `/usage` shows them. **GitHub Copilot** (specs/018): `copilot/hooks/turn-tokens.json` adds an `agentStop` hook through the same `~/.copilot/hooks` link, for the Copilot CLI and the Copilot agent in VS Code; it needs no trust step. The CLI shows the report as progress lines after each turn. Reload VS Code (Developer: Reload Window) so its Copilot reads the new hook and the current instructions. When a session's context passes 100,000 tokens, the report adds a `Cache ·` line with the time its prompt cache expires, and a desktop notification comes 2 minutes before that, unless the session continued (TT-17, TT-18; on macOS, allow notifications for Script Editor the first time). `TURN_TOKENS_REMIND=off` turns the notification off, and `TURN_TOKENS_REMIND_LEAD_MIN` changes the 2 minutes.
13. **Turn on the workflow guard** (`specs/019-workflow-graph/`). It needs Node.js 24.12 or later (it runs TypeScript directly) and `pnpm install` in the repo for its own checks. **Copilot CLI:** `copilot/hooks/workflow-graph.json` (`preToolUse`, `userPromptSubmitted`) is live through the `~/.copilot/hooks` link; it is installed at user level because Copilot loads a project's `.github/hooks/` only in a trusted folder (tested 2026-11-03). **Codex:** `codex/hooks.json` now has `PreToolUse` and `UserPromptSubmit` hooks; trust both in `/hooks`. **Claude Code:** merge `hooks.PreToolUse` and `hooks.UserPromptSubmit` from `claude/settings.json` into `~/.claude/settings.json` (back it up first; don't edit it for the user). The guard acts only on launches whose prompt names a `run:` and on edits to `.specify/runs/`; every other tool call is left alone (about 0.1 s per call). To switch it off, start the agent with `AGENTIC_SDLC_GUARD=off`; `check-run` then warns about each unguarded launch. Confirm: in a project, `node ~/.copilot/frameworks/agentic-sdlc/tools/workflow-graph/src/main.ts status` answers `No open runs in …`.
14. **Optional: the headless workflow runner** (`specs/020-workflow-runner/`). It drives a run by itself: `node ~/.copilot/frameworks/agentic-sdlc/tools/workflow-graph/src/main.ts run start R-007 --path new-feature --feature specs/023-cart --agent claude-code [--role-agent qa=copilot-cli] [--check "pnpm test"] [--max-usd 2] [--timeout-minutes 30]` in the project. Each role runs headless (Claude Code, Copilot CLI or Codex) with write access only in execute mode, in a git worktree beside the project (`<project>.runs/R-007`, branch `run/R-007`; P6 tasks in `<project>.runs/R-007-T001`, merged back after review); your checkout is not written. At each gate it stops: approve with `… run approve R-007 G3 "your words"` in a terminal (it reads your confirmation from the terminal), or type `approve G3 R-007` in a chat session and run `… run resume R-007`. It needs `pnpm install` in agent-config (LangGraph.js and a native SQLite module, loaded only by `run`); Codex's program can be set with `WORKFLOW_GRAPH_CODEX=<path>` (on a Mac with the ChatGPT app: `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`).
15. **Optional: the weekly efficiency audit** (`proposals/efficiency-auditor.md`). Nothing to install: it runs from this repo with Node.js 18 or later and only reads the agents' logs. Tell the user it exists: `node copilot/efficiency-audit/efficiency-audit.mjs week` once a week. It keeps its history in `~/.copilot/efficiency-audit/history.jsonl`, which is not linked to the repo. How to read and act on the report: `copilot/knowledge/ai-agents/audit-agent-efficiency.md`.

## What NOT to do

- Don't hand-edit `core.instructions.md` to record this machine's repo path — that file is git-tracked and meant to be byte-identical across every machine. The machine-specific value belongs only in the `seed-once`-deployed `global-variables.md`, never in a symlinked/tracked file.
- Don't re-run steps 3–5 on a machine where the relevant variable is already filled in correctly — nothing breaks if you do, but there's no reason to.
- Don't skip step 6's confirmation just because detection seems obviously correct.
- Don't invent a per-company file for company repo-root variables — they belong in `global-variables.md` alongside `{{AGENT_CONFIG_REPO}}`, for the same reason `{{AGENT_CONFIG_REPO}}` isn't in `core.instructions.md` (see `global-variables.md`'s "Company repo roots" section for the exact constraint).
